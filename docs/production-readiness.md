# O Moto Shop — acompanhamento de prontidão para produção

Este documento é o quadro de acompanhamento do MVP. Ele separa evidências já obtidas, trabalho que pode avançar no código e dependências externas. Uma etapa só muda para **validada** quando houver evidência registrada; configuração presente no `.env.local` não significa que esteja disponível em produção.

## Estado geral

O projeto tem uma base funcional de marketplace e uma suíte automatizada aprovada nos fluxos cobertos, mas **ainda não está pronto para produção**. O principal bloqueador de negócio é definir e homologar o modelo de pagamento multi-lojista. Não considerar pagamento, split, refund ou webhook financeiro prontos para vendas reais até essa homologação.

## Dependências externas / bloqueadores

### Banco oficial e publicação

- [ ] Responsável fornecer/criar a instância PostgreSQL/Neon **de produção**, separada do banco de testes, com URLs pooled e direct apropriadas. Nunca migrar, apagar ou semear dados de demonstração no banco oficial sem autorização explícita.
- [ ] Acesso autorizado ao projeto Vercel correto e confirmação das variáveis de produção. `.env.local` é local e não configura o deploy.
- [ ] Para ativar a configuração de Sandbox, o responsável pelo Vercel precisa autorizar o autor Git `GuiSatierf` (autor do `HEAD` local usado na tentativa) ou realizar o deploy Preview com uma identidade autorizada. Não contornar essa validação nem promover para Produção.
- [ ] Definir URL canônica e origem HTTPS final; configurar `BETTER_AUTH_URL`, origens confiáveis/callbacks e domínios de produção conforme a URL confirmada.
- [ ] Planejar primeira migração (`prisma migrate deploy`), backup/restore e procedimento de rollback antes de abrir vendas.

### Mercado Pago — bloqueador de venda online

- [ ] Responsável confirmar com Mercado Pago qual modalidade de marketplace/split está habilitada para a conta e homologar um checkout com mais de um seller. Não presumir que split 1:N ou split 1:1 esteja disponível.
- [ ] Credenciais OAuth da aplicação e autorização das contas de teste dos sellers, caso o modelo aprovado exija conexão de vendedores.
- [ ] Definir e configurar URL pública de webhook e segredo de assinatura; testar assinatura, repetição, atraso e reprocessamento em ambiente de homologação.
- [ ] Validar pagamento aprovado, recusado, pendente, cancelamento e refund somente com contas/cartões de teste e provider habilitado para o modelo aprovado.
- [ ] Até esses pontos passarem, manter checkout real bloqueado. O provider atual não oferece split para sellers e refund real não está suportado.

## Sequência sugerida para fechar o MVP

1. Concluir revisão dos fluxos sem dependências externas e corrigir os defeitos encontrados.
2. Receber banco oficial, acesso de deploy e catálogo aprovado; preparar produção isolada, sem dados de teste.
3. Resolver a modalidade multi-seller com Mercado Pago e concluir homologação financeira. Se não houver modalidade aprovada, manter compras reais desabilitadas e registrar a decisão de produto.
4. Configurar ImageKit, e-mail, frete, workflows e observabilidade conforme os serviços que serão usados no lançamento.
5. Aplicar migrations e executar smoke tests autorizados em ambiente de homologação, incluindo pagamento apenas com contas de teste.
6. Fazer checklist de segurança, backup/restore, domínios, monitoramento e rollback; só então solicitar autorização para publicar/abrir vendas.
